# Baseline-relative gait timing experiment

This independent Arduino sketch tests one part of the ECE 590 StrideGuard proposal: sustained stride-timing deviation relative to an initial running baseline. All input timestamps are generated by the simulation. No IMU or BLE connection is required.

## Two files, one new sketch

Keep both files together:

```text
gait_stability_sim/
  gait_stability_sim.ino
  GaitStabilityDetector.h
```

Open `gait_stability_sim/gait_stability_sim.ino` in Arduino IDE. The header is automatically included through `#include "GaitStabilityDetector.h"`. If the IDE does not display it, use the sketch-folder menu to confirm that it exists beside the `.ino`. Do not paste this `.ino` into either original firmware sketch: it has its own `setup()` and `loop()`.

Select the actual wrist board and USB port, then verify/upload. For the team's Adafruit ESP32-S3 Feather, use the exact board variant and USB settings already validated by the team. Uploading this sketch replaces the running wrist firmware; the original source remains in `firmware/wrist_full_system_test/` and can be uploaded again to restore the BLE hardware test.

The default sketch needs only the Arduino ESP32 board package. It does not initialize either IMU, BLE, or the motor. Open Serial Monitor at **115200 baud**, reset the board if needed, and wait about **22.5 seconds** for `BASELINE_READY`.

## Manual tests

Type a command into Serial Monitor and press Enter. Either uppercase or lowercase works.

| Command | Input scenario | Expected behavior |
| --- | --- | --- |
| `n` | Normal intervals: 750, 760, 740, 755, 745 ms | Remain stable; after an unstable episode, recover after two low windows |
| `u` | Sustained irregular intervals: 500, 1000, 550, 950, 750 ms | Become `SUSPECT`, then `UNSTABLE` and emit `ALERT` after two high windows |
| `s` | One 1100 ms interval, followed by normal timing | A single disturbed window should not produce an alert when starting from stable normal timing |
| `p` | Pause/resume | Pause generation while retaining valid calibration progress and the learned baseline |
| `r` | Reset | Start a new normal calibration |
| `v` | Manual output test | Exercise the output independently of the detector |
| `?` | Help | Print commands and CSV column names |

`u` and `s` are disabled until calibration completes. Use `r` between independent experiments. For recovery testing, use `n` without resetting. A complete window is five intervals; switching scenarios mid-window can delay a full scenario window. Normal intervals average 750 ms; the unstable pattern also averages 750 ms, so the experiment changes variability rather than mean pace.

Output is CSV with `#` comment lines. `NA` means no complete window is available. The final `alert` column is an event: `1` only on an eligible transition into instability, not a continuously asserted state. `UNSTABLE` is the persistent state until recovery.

## Algorithm

1. Accept one timestamp for each successive strike of the **same foot**. Calculate interval using unsigned millisecond subtraction.
2. Ignore duplicate/short intervals below 350 ms. An interval over 2500 ms is excluded as a gap. Calibration progress and the learned baseline are retained; monitoring evidence is cleared and the next interval uses a fresh reference. These bounds are configurable prototype assumptions.
3. Use non-overlapping windows of five intervals. Calculate population standard deviation divided by mean, multiplied by 100: `CV = SD / mean * 100`.
4. Calibrate on six normal windows (30 intervals). Baseline CV is the mean of those six window CV values. It remains fixed until explicit reset or device restart. Valid calibration intervals may accumulate across interrupted segments; no interval crossing a gap is counted.
5. Experimental entry threshold: `max(2 * baselineCV, baselineCV + 3 percentage points)`. Require two consecutive high windows before entering `UNSTABLE`.
6. Experimental recovery threshold: `max(1.5 * baselineCV, baselineCV + 1.5 percentage points)`. Require two consecutive low windows to recover.
7. Emit one alert on entry, with a 10-second simulation-clock cooldown. An entry during cooldown changes the state without producing another motor command. Continued instability does not repeatedly vibrate.

These are research parameters, not thresholds established by the proposal or validated with runners. A constant change of pace has low steady-state CV; a sudden transition can still disturb a mixed window. Long or repeated ordinary pace changes may trigger this timing detector. Future evaluation must include turns, changes of speed, surfaces, missing events, and mounting changes.

## Optional physical vibration

At the top of the `.ino`, change `ENABLE_HAPTICS` from `0` to `1`. Install the Adafruit DRV2605 Library and dependencies, connect the existing DRV2605L plus ERM motor, and ensure `Wire.begin()` matches the board's actual I2C wiring.

- Disabled or unavailable driver: `HAPTIC_SIMULATED`; no motor command is sent.
- Initialized driver: `HAPTIC_COMMAND_SENT`; this reports a command, not independently verified motor motion.

No IMU or foot node is required even with this option enabled.

## Later integration with the real firmware

The current real firmware does not extract foot strikes. Do not call `observeStride()` for every raw BLE packet: packet time is not a foot-strike time. Add and validate event extraction at the shoe node, then send event timestamps or equivalent validated features.

After that, the wrist sketch can include this header, create a detector instance, feed same-foot event timestamps, and use `result.alert` to call its existing vibration routine. The original wrist sketch must keep its own `setup()` and `loop()`; do not merge the simulation sketch into it. Handle link loss, no-data timeouts, calibration, and session resets explicitly.

This experiment does not implement stance/swing duration, impact analysis, bilateral asymmetry, or wrist motion context. It does not establish that a timing deviation was caused by fatigue. Those remaining proposal features need separate implementation and physical validation.

## Validation

The portable detector has 16 automated C++ tests for calibration, normal timing, transient disturbances, sustained instability, recovery, a steady pace change, rejected duplicate events, gaps, timestamp rollover, baseline adaptation, cooldown, partial calibration retention, foot-clock restart, and isolation of alert evidence across pauses.

From the repository root on a machine with a C++11 compiler:

```sh
g++ -std=c++11 -Wall -Wextra -Werror -pedantic algorithm_demo/tests/gait_stability_test.cpp -o /tmp/gait_stability_test
/tmp/gait_stability_test
```

Passing host tests establishes the software decision logic on those inputs. It does not establish ESP32 compilation, physical motor operation, foot-strike extraction accuracy, or detection performance on real runners.
